### 테스트 (커밋 `4eec25c`)

간헐적 1건 실패의 근본 원인을 특정했다. `vitest.config.ts`의 `testTimeout: 30000`은
RTL의 `waitFor`/`findBy`에 적용되지 않고, RTL은 자체 기본값 **1초**를 쓴다. 테스트 파일이
병렬로 도는 동안 jsdom 렌더가 1초를 넘기면 "0 times 호출됨" 같은 일반 단언 실패로 나타난다.
재현된 사례는 `src/pages/ChildPhotosScreen.test.tsx`의 GPS 마스킹 테스트이며 격리 실행에서는
8/8 통과했다. `vitest.setup.ts`에 `configure({ asyncUtilTimeout: 5000 })`을 추가해 129개
호출부를 한 번에 덮었다. 개별 파일에 있던 `{ timeout: 3000 }` 임시 조치 2곳도 이것으로 대체된다.

공유 SQLite DB나 업로드 디렉터리 경합은 **원인이 아님을 확인했다**. 두 서버 테스트 파일은
각자 `os.tmpdir()`에 다른 접두사로 DB를 만들고, pool `forks` + `isolate: true`라 프로세스가
분리된다.

하드닝:

- `POST /api/auth/phone`에 시도 제한을 붙였다. 번호별 10회 / IP별 100회 / 10분 창이며

  NAT 뒤에서 같은 IP로 잡히기 때문이다. 번호를 노린 대입은 번호 한도가 막는다.
  프로세스 메모리 기반이라 다중 인스턴스에서는 공유 저장소가 필요하다(`ponytail:` 주석으로 표시).

## PDF 렌더링 브라우저 재사용 (커밋 아래 참조)

`renderHtmlToPdf`가 **호출마다 Chrome을 새로 띄우고 닫았다.** 출판 요청 하나가 브라우저 기동을
여러 번 반복했고, 테스트에서는 부하가 걸리면 `testTimeout: 30000`을 넘겼다.
프로세스당 한 번만 띄우고 재사용하도록 바꿨다.

- 동시 호출은 같은 promise를 공유한다. 캐시 대입이 `await`를 건너뛰지 않으므로 중복 기동이 없다.
- 크래시로 끊긴 브라우저는 `connected`로 감지해 다시 띄운다.
- 실패한 promise는 캐시에 남기지 않는다. 남기면 이후 모든 호출이 같은 오류를 되받는다.
- 호출마다 페이지만 닫는다(`page.close()`). 안 닫으면 탭이 쌓인다.
- `closeRenderBrowser()`를 내보내 테스트 `afterAll`에서 Chrome을 정리한다.

측정(로컬, 부하 없는 상태에서 `server/app.test.ts` 2회씩):

| | 소요 |
| --- | --- |
| 변경 전(호출마다 기동) | 10.59s, 11.02s |
| 변경 후(프로세스당 1회) | 9.24s, 8.43s |

부하가 걸린 상태에서는 기동들이 CPU를 두고 경합하므로 차이가 더 커지지만, 이번에 측정한 것은
부하 없는 상태다. 새로 추가한 `server/publication-html.browser.test.ts`는 PDF 5장을 2.15초에
만든다. 누수 확인: 테스트 후 `--font-render-hinting=medium` 프로세스 0건.

전체 스위트는 6회 연속 251개 통과했다.

## 5종 동의 집행 (커밋 아래 참조)

조사에서 드러난 근본 문제는 **동의가 운영에서 생성되지 않는 테이블에 붙어 있었다**는 것이다.
`prisma.memory.create`는 테스트에만 존재하고, 실제 답변은 전부 `InterviewRecord`가 된다.
그래서 5종 동의 화면은 실사용에서 늘 비어 있었다(데모 시드에서만 항목이 보였다).

동의를 실제 데이터가 있는 곳으로 옮기고 소비 지점에서 강제했다.

| 목적 | 집행 지점 |
| --- | --- |
| `publish` | 출판 파이프라인, 표지 에이전트, 자서전 초안 |
| `familyRead` | 보호자 대상 `/api/interview-records`, `/api/free-speech`. 본문과 **음성을 함께** 가린다(텍스트만 가리면 오디오로 들린다). 부모님 본인 조회는 유지 |
| `chatbot` | 챗봇 chunk 생성 |
| `posthumous` | 유산 전수 후에도 철회한 기록은 계속 가린다 |
| `sensitive` | 출판 입력, 표지 에이전트, 챗봇, 자서전 초안 — 외부 AI 제공자로 나가는 경로 전부 |

부수적으로 고친 것:

- `FreeSpeechRecord`가 `InterviewRecord`를 **복사**해 만들어지면서 동의 필드가 없어 우회로였다.
  사본에 동의를 복제하면 진실의 원천이 둘이 되므로, `interviewRecordId`로 원본을 가리키고
  동의를 원본에서 읽게 했다. 기존 행은 마이그레이션에서 역참조를 복구하고, 복구하지 못한 행은
  철회로 간주해 가린다.
- 데모 시드가 `{ publish: true, chatbot: true }`로 하드코딩해 시드에 들어 있던 철회 상태
  (예: 민감정보 revoked)를 버리던 것을 5종 그대로 옮기도록 고쳤다.
- 낙관적 갱신이 서버 실패 시 되돌아가지 않던 것을 고쳤다. 화면만 바뀌고 서버는 그대로면
  동의한 줄 아는 상태가 남는다.

마이그레이션은 `ALTER TABLE ADD COLUMN`만 쓰는 가산적 변경이며, 기존 행은 모두 허용 상태로
둔다(철회는 사용자가 명시적으로 하는 행위이므로 마이그레이션이 임의로 철회하지 않는다).
예전 스키마를 재현한 DB에 적용해 새 컬럼 추가, 기존 `chatbot=0` 보존, 사본→원본 역참조 복구를
확인했다.

### 2단계: 사진 동의

사진에 `publish` / `familyRead` / `posthumous` / `sensitive` 4종을 붙였다. `chatbot`은 두지
않았다. 분신 대화는 사진을 근거로 쓰지 않고, 집행 지점 없는 컬럼을 만드는 것이 애초에
이 문제를 만들었기 때문이다.

- `publish`: 출판 파이프라인의 사진 조회. 예전에는 모든 사진이 무조건 책에 들어갔다.
- `familyRead`: `/api/photos`에서 목록에서 아예 뺀다. 사진은 URL 하나만 남아도 보인다.
- `posthumous`: 유산 전수 후에도 철회한 사진은 열리지 않는다.
- `sensitive`: 업로드 시 `sensitive: false`면 AI 분석 자체를 하지 않는다. 사진 분석은
  업로드 시점에 일어나므로, 올린 뒤에 끄면 이미 늦기 때문이다.

동의 화면에 사진 섹션을 추가해 사용자가 실제로 설정할 수 있게 했다.

### 3단계: 철회의 소급 적용

동의를 철회해도 **이미 만들어진 PDF는 그대로 남았다.** `resolveLocalFileAccess`가
`publicationRequest`를 `pdfFileKey`로 찾아 소유권만 확인하고 동의는 전혀 보지 않았다.
부모님이 어떤 기록의 `publish`를 철회해도 그 기록이 담긴 책을 가족이 계속 내려받았다.

**기존 PDF를 무효화한다.** 종이책은 회수할 수 없지만 PDF는 막을 수 있고, 막을 수 있는 것까지
놔두면 동의 기능 전체가 무의미해진다.

철회할 때 영향받는 책을 찾아 표시하는 대신, **여는 시점에 "이 책을 만든 뒤에 동의가 철회된 적이
있는가"만 본다.** 집행 지점이 하나라 빠뜨릴 구멍이 없다. 철회 시각은 `InterviewRecord`/`Photo`에
추가한 `consentUpdatedAt`으로 안다. 두 표에는 `updatedAt`이 없고, 있었더라도 본문 수정까지
잡아 멀쩡한 책을 막았을 것이다.

- `GET /api/files/pdfs/*`: PDF에 도달하는 유일한 경로. 서명 토큰 경로와 로그인 경로가 여기서 만난다.
- `GET /api/publication-preview-jobs/:id`: 예전 job id로 조회하면 철회 전 초안 HTML이 그대로 열렸다.
- 막을 때 `404`가 아니라 `409`와 "다시 만들어 주세요" 메시지를 준다.
- 부모님 본인은 계속 볼 수 있다. 기존 동의 집행과 같은 원칙이다.
- 미리보기 초안 캐시는 `sourceHash`가 이미 동의로 걸러진 목록에서 계산돼 우회로가 아니었다.

`server/revocation-retroactive.test.ts` 7건을 추가했다. 게이트를 일시 제거해 4건이 실제로
실패하는 것을 확인한 뒤 복원했다.

**이어서 막은 구멍(2026-08-03): 삭제의 소급 적용.** 지운 행에는 `consentUpdatedAt`을
남길 자리가 없어 철회는 막히고 삭제는 그대로 열렸다. `User.publicationContentDeletedAt`에
시니어 단위로 "마지막으로 지운 시각" 하나만 남기고 같은 게이트가 함께 본다. 책에 애초에
들어가지 않던 것(`publish=false` 또는 `sensitive=false`)을 지운 것은 남기지 않는다.

### 간헐적 테스트 실패의 정체

`server/app.test.ts`의 `caches publication preview output…`이 이름으로 특정됐다.
전체 에이전트 파이프라인과 실제 PDF 렌더링을 도는 테스트라 전역 `testTimeout`(30초)이
병렬 실행에서 빠듯했다. 멈춘 것이 아니라 느린 것이므로, 출판 관련 무거운 테스트 5건에만
`120_000`을 지정했다. 이후 전체 스위트 5회 연속 통과했다.

`server/consent-enforcement.test.ts` 18건을 추가했다. 검증: lint 통과,
32 files / 271 tests 통과(연속 5회), build 통과. 예전 스키마를 재현한 DB로
`InterviewRecord`와 `Photo` 마이그레이션을 각각 확인했다.

## 수정하지 않고 남긴 것

임의로 처리하면 안 되는 제품·정책 결정이라 보고만 한다.

### 큰 결정이 필요한 것

1. ~~**동의 모델 이중화 해소.**~~ 해결됨. 5종 동의를 `InterviewRecord`로 옮기고
   소비 지점에서 강제한다. `docs/consent-enforcement-design.md`와 아래 "5종 동의 집행" 참조.
2. ~~**철회의 소급 적용.**~~ 해결됨(PDF·미리보기 초안·기록 삭제). 이미 만들어진 책은
   만든 시점 이후에 출판 동의가 철회되거나 책에 들어갔던 내용이 지워지면 더 이상 열리지 않는다.
   `docs/consent-enforcement-design.md`와 아래 "3단계: 철회의 소급 적용" 참조.
   `FreeSpeechRecord` 사본은 원본 역참조로 이미 해결됐고, 챗봇 대화 기록의 localStorage
   인용문은 남아 있다(서버가 지울 수 없는 저장소라 화면이 지워야 한다).
3. **죽은 코드 삭제.** 일부는 처리했고(아래 "죽은 코드 정리" 참조) 다음이 남아 있다:
   - 디지털 유산 금고 전체(약 1,100줄): 라우트 6개, 클라이언트 래퍼 6개, `shamir.ts`/`encryption.ts`
     (importer 0), `LegacyVault` 모델. 이를 호출하는 화면이 없다. **다만 `LegacyVault` 모델이
     `/api/memories`, `/api/interview-records`, `/api/free-speech`의 마스킹 분기에 물려 있고
     테이블 마이그레이션이 필요하다.** 라우트를 지우면 `isVaultSetup`을 켤 방법이 사라져
     마스킹도 영구히 죽으므로, 사실상 "미완성 기능을 접는" 결정이다. 제품 판단이 먼저다.
   - Web Push + app-call 계열(약 500줄): `registerLocalPushSubscription` 호출부가 0건이라
     서비스 워커가 등록되지 않는다. 알림은 현재 **쓰기 전용**이다. 다만 `sendWebPush`는
     AI 프록시 알림·넛지·비활동 알림에서 호출되므로 절반만 지우면 안 된다.
     읽는 쪽을 살릴지 쓰는 쪽을 지울지 결정해야 한다.

### 알려진 문제로 남긴 것

- **출판 미리보기 재시도 무한 루프 가능**: `PUBLICATION_PREVIEW_MAX_ATTEMPTS`가
  `isRecoverablePreviewJobError`로 감싸여 있어 복구 가능 오류에서는 상한이 적용되지 않는다.
- **PDF 생성 실패 시 `generating` 상태 고착**: `failed` 전이가 없어 UI가 진행 중과 구분 못 한다.
- **챕터 정의 3중화**: `server/domain/constants.ts`(7개), `demo-seed-adapter.ts`(5개),
  `ChildQuestionsScreen.tsx`(5개)가 같은 id에 서로 다른 한국어 제목을 쓴다. 어느 쪽이
  맞는지는 제품 결정이다.
